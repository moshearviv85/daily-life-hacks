## 2. Filenames

### 2.1 Verdict: do not rename the heroes

Filenames are in good shape. `{slug}-main.jpg` puts the full keyword phrase in the path, which is what the ranking signal actually reads. The `-main` suffix is dead weight but carries no penalty.

Renaming is **blocked three ways** and not worth it:

1. **Validator rule S-08** (`scripts/article_spec.md:27`, `scripts/NEW_PIPELINE_2026-05-08/lib/validator.py`) requires `image` to equal `/images/{slug}-main.jpg` exactly. Any rename means editing the validator, which changes the pipeline's contract.
2. 234 frontmatter edits in `src/data/articles/`, which I do not own.

## 3. Formats, size, dimensions, lazy loading — what I changed

### 3.1 `scripts/optimize-images.mjs` — coverage, honest widths, a manifest

**Changed:** the source filter went from `f.endsWith("-main.jpg")` to every JPEG directly under `public/images/`. Subdirectories (`pins/`, `video/`, `drafts/`, `test-*/`) stay excluded — none render on the site.

Result: **59 previously-unoptimised images now get WebP at 400/800/1200w**, including all 31 charts.

Measured on those 59 files: **6.1 MB of source JPEG → 1.5 MB at the 800w tier, a 75% reduction.**

**Changed:** it now writes `public/images/opt/manifest.json` recording each source's intrinsic `width`/`height` and the **actual** pixel width of each generated variant.

This fixes a real latent bug. The old srcset was hardcoded to `400w, 800w, 1200w` regardless of the source. `sharp` never upscales (`Math.min(w, meta.width)`), so a 768px-wide source produced a file named `-1200w.webp` that is 768px wide, and the browser was told it was 1200px. It would then pick that candidate on a wide viewport and render it upscaled and soft. The manifest makes the srcset describe reality, and de-duplicates when two requested widths collapse to the same real width.

**Deliberately did NOT add AVIF.** `public/images/opt/` is gitignored, so CI regenerates every variant on every deploy. Measured on this machine: WebP encodes all 293 images × 3 widths in **67 s** cold (up from ~55 s before the coverage increase — the 59 extra files cost 12 s). AVIF at the same coverage benchmarks **5.8× slower** (1,408 ms vs 244 ms for one image at three widths), i.e. roughly **+7 minutes on every deploy**, for a marginal byte saving that has **no effect on image-search ranking** — Google Images ranks the image, not its container format. The rationale is in the file header so nobody re-litigates it.

**Added:** the optimiser now calls `scripts/build-image-sitemap.mjs` at the end (§4), so the sitemap regenerates from the same prebuild hook with no `package.json` change.

### 3.2 `src/components/OptImage.astro` — the broken-`<picture>` trap

**The bug:** a `<source>` inside `<picture>` is a commitment. If the browser matches `type="image/webp"` and the file 404s, it does **not** fall back to the `<img>` — it renders a broken image. The old component emitted three WebP `<source>` URLs unconditionally, whether or not those files existed.

That was live on the nine articles in §1.5 and would fire again for any image the optimiser has not processed (e.g. anyone running `astro dev` without a prebuild — the whole site would show broken images).

**Fix:** the component reads the manifest at build time. If an entry exists it emits `<picture>` with a truthful srcset; if not it emits a plain `<img src>`. Verified in `dist/`:

```html
<!-- dist/animal-protein-per-dollar-ranked/index.html — variants exist -->
<picture><source type="image/webp" srcset="/images/opt/…-400w.webp 400w, …-800w.webp 800w, …-1200w.webp 1200w" sizes="(max-width: 768px) 100vw, 768px"><img src="/images/animal-protein-per-dollar-ranked-main.jpg" … width="768" height="432" loading="eager" decoding="sync" fetchpriority="high"></picture>

<!-- dist/tofu-vs-chicken-protein-cost/index.html — hero missing on disk -->
<img src="/images/tofu-vs-chicken-protein-cost-main.jpg" … width="768" height="432" loading="eager" decoding="sync" fetchpriority="high">
```

`grep -c "images/opt/tofu-vs-chicken" dist/tofu-vs-chicken-protein-cost/index.html` → `0`. No phantom `<source>`.

**Also added:** intrinsic `width`/`height` now fall back to the manifest when a caller omits them, so no OptImage call site can produce CLS by accident.

### 3.4 The remaining gap: in-body markdown images (needs your 2-line diff)

**49 in-body `<img>` tags ship with no `width`, no `height`, no `loading` and no WebP.** These are the charts. Astro compiles `![alt](/images/x-chart.jpg)` to a bare tag:

```html

```

No intrinsic size → layout shift on every data article. No `loading="lazy"` → every chart competes with the hero for initial bandwidth.

I wrote and tested the fix as `scripts/rehype-article-images.mjs`. It reads the same manifest, adds `width`/`height`/`loading="lazy"`/`decoding="async"`, and wraps the tag in a `<picture>` with the WebP srcset. It leaves any image not in the manifest completely untouched — no phantom `<source>`, ever. `<picture>` is phrasing content so it is valid inside the `<p>` markdown wraps a standalone image in.

```

## 4. Image sitemap — SUPERSEDED mid-session (read this)

**Status: done, but not by me. Another agent implemented it in `astro.config.mjs` while I was working, using the approach I had recommended. My standalone version has been removed. Nothing here is outstanding except one gap in §4.4.**

### 4.1 What I originally built, and why it is gone

`astro.config.mjs` emitted no image entries at the start of this session. Since I do not own that file, I built a standalone generator (`scripts/build-image-sitemap.mjs` -> `public/image-sitemap.xml`, wired into the prebuild hook via the optimiser, referenced from `robots.txt`), validated it, and wrote the `astro.config.mjs` diff into this report as the better long-term option.

Partway through, another agent implemented exactly that better option: `loadArticleImages()` in `astro.config.mjs` now attaches `img` entries to each URL in the existing `@astrojs/sitemap` `serialize()` hook, so image data ships **inside `sitemap-index.xml`** — already referenced from `robots.txt`, no second crawl target. Their reasoning in-file matches mine:

> "Google's own documentation allows image extension tags inside a normal sitemap, and at ~240 URLs a second sitemap file would add a crawl target for no benefit."

**This is the right outcome and I have not tried to reinstate my version.** Their implementation is also better in one respect: it reads from `serialize()`, which only ever sees post-exclusion URLs, so alias slugs and unreleased articles are filtered by construction rather than by my duplicated logic.

### 4.2 Cleanup I did as a result

Their change removed my two files but left two artefacts behind, both of which I have fixed:

- `scripts/optimize-images.mjs` (**mine**) was left **syntactically broken** — the JSDoc header was truncated mid-block so the `*/` terminator was gone, taking the whole `import` section into the comment. `npm run build` failed at prebuild with `ERR_MODULE_NOT_FOUND`. Repaired; `node --check` clean.
- `public/robots.txt` had my `Sitemap: …/image-sitemap.xml` line removed but left a **dangling three-line comment fragment** referencing a script that no longer exists. Since `public/image-sitemap.xml` is no longer generated, that directive would have pointed at a 404. I reverted the file to its committed state with `git checkout` — it is now clean, and `git status` shows it unmodified.

### 4.3 Validation (from my version, still informative)

Before it was superseded, I validated the generated XML against **both** published schemas using `lxml` — the core `sitemaps.org/schemas/sitemap/0.9` XSD and Google's `sitemap-image/1.1` XSD, both fetched live:

```

image:image elements: 268  | image extension XSD: OK
core sitemap 0.9 XSD:                              OK
url entries: 210 (limit 50,000)

Element order matched the XSD sequence (`loc` then `caption`). **Worth re-running against the new inline output** — I have not validated the `@astrojs/sitemap` `img` emission, only my own.

**Know this about `image:caption`:** Google **deprecated** `<image:caption>`, `<image:title>`, `<image:license>` and `<image:geo_location>` — announced May 2022, effective **2022-08-06** ([Search Central Blog, "Spring cleaning: sitemap extensions"](https://developers.google.com/search/blog/2022/05/spring-cleaning-sitemap-extensions)). Only `<image:loc>` is read. The new implementation passes captions too. They are valid and harmless, and Bing's handling is undocumented, so leaving them is defensible — **but nobody should believe they are doing anything for Google.** The alt text on the page is what carries.

### 4.4 The one real gap left in their version

`loadArticleImages()` collects three things: frontmatter `image`, markdown `![alt](/images/…)`, and raw `<img src="/images/…">` **in the article body**. It does **not** collect `/images/{slug}-ingredients.jpg`.

That is the one class of image where a sitemap is the *only* discovery route. Those images are injected client-side by `src/pages/[slug].astro:1113` after page load — they are **not in the served HTML at all**, and [Google's lazy-loading guidance](https://developers.google.com/search/docs/crawling-indexing/javascript/lazy-loading) (updated 2025-12-10) is explicit that Google does not scroll or click, so image URLs must be in the rendered `<img>` `src` to be found. Nine of these exist today.

Suggested addition for whoever owns `astro.config.mjs`, inside the per-article loop in `loadArticleImages()`, right after the two `matchAll` blocks:

```js
    // Injected client-side by [slug].astro, so it never appears in the served
    // HTML. The sitemap is its only discovery route. Absent for most articles;
    // the existsSync filter below drops it silently when missing.
    const ingredients = `/images/${slug}-ingredients.jpg`;
    if (!found.has(ingredients)) found.set(ingredients, undefined);
```

Their existing "never advertise an image that this build does not actually ship" `readFileSync` guard already handles the ~200 articles that have no such file, so this is safe as written. Ideally pair it with the alt-text fix in §5.2 Gap 4 — `img.alt = "Ingredients"` is a wasted slot on exactly the kind of image ("ingredients for X laid out on a counter") that image search actually serves.

### 5.2 Gaps

**Gap 1 — the charts are in no schema at all.** 31 original data charts + 17 data graphics appear in the rendered HTML and now in the image sitemap, but nothing in `Article.image` or `Recipe.image`. For a data-driven article the chart is arguably the more distinctive image. `Article.image` accepts an array; appending the in-body images is straightforward in `[slug].astro`.

**Gap 2 — `ImageObject` carries no dimensions or caption.** Google's structured-data guidance asks for `width`, `height` and `caption` on `ImageObject`. All of that is now available for free from `public/images/opt/manifest.json` (`entry.width`, `entry.height`) plus `imageAlt`. Recommended shape:

```json
"image": [{
  "@type": "ImageObject",
  "contentUrl": "https://www.daily-life-hacks.com/images/{slug}-main.jpg",
  "url":        "https://www.daily-life-hacks.com/images/{slug}-main.jpg",
  "width": 1376, "height": 768,
  "caption": "<imageAlt>"
}]
```

**Gap 3 — one aspect ratio.** Google's Article and Recipe docs recommend supplying 16×9, 4×3 *and* 1×1 crops so the layout engine can pick. Every hero is 16×9 only. I can generate 4:3 and 1:1 crops in the optimiser — but blind centre-cropping AI food photography will decapitate subjects, so this needs a look before it ships. Say the word and I'll do it with a review pass.

**Gap 4 — the mid-article ingredients image is invisible to structured data and has generic alt.** `[slug].astro:1113` sets `img.alt = "Ingredients"` for every one of them. Two fixes, both in a file I don't own:

```diff

+++ b/src/pages/[slug].astro
@@ -1108
-      img.alt = "Ingredients";
+      img.alt = main.getAttribute("data-ingredients-alt") || "Ingredients";
       img.loading = "lazy";
+      img.width = 1376;

```

…with `data-ingredients-alt` rendered server-side from a new optional `ingredientsAlt` frontmatter field. `"Ingredients"` on nine images is a wasted alt slot on the exact kind of image ("ingredients for X laid out on a counter") that image search actually serves.

**Gap 5 — no licensing metadata, and the Licensable badge is still live.** No `license` / `acquireLicensePage` on any `ImageObject`.

The Licensable badge **still exists in 2026** — [Google's image-license-metadata doc](https://developers.google.com/search/docs/appearance/structured-data/image-license-metadata) was last updated **2025-12-10** with no deprecation notice, and it is explicit: *"If you're using structured data to specify an image, you must include the `license` property for your image to be eligible to be shown with the Licensable badge."* Required: `contentUrl` plus at least one of `creator` / `creditText` / `copyrightNotice` / `license`; `acquireLicensePage` recommended.

Do not confuse this with the sitemap `<image:license>` element, which **was** deprecated in 2022. The structured-data property is alive.

**Still blocked, though.** Same unresolved licence question that blocks Dataset Search (C6 in the traffic sweep: the CC BY page was added and then reverted in `207442c`). Do not add licence claims until someone establishes why that was pulled. Resolving it unlocks both surfaces at once, which makes it worth more than it looks.

## 6. The honest ceiling

### 6.1 Is AI-generated imagery disadvantaged in image search in 2026?

**No documented demotion. Google has denied it on the record, twice.**

- **Gary Illyes**, Google, Q&A with Kenichi Suzuki, reported 2025-08-11: *"No, no. So AI generated image doesn't impact the SEO. Not direct… If anything, you might get some traffic out of image search or video search or whatever, but otherwise it should just be fine."* ([SEJ](https://www.searchenginejournal.com/google-says-ai-generated-content-will-not-cause-ranking-penalty/553465/))
- **Ian Huang**, Google, Search Central Live APAC, 2025-07-24: *"Google doesn't care whether your images are generated by AI or humans, as long as they accurately and effectively convey the information or tell the story you intend."* ([SEJ](https://www.searchenginejournal.com/google-search-central-apac-2025-everything-from-day-two/551941/))

**Labelling is disclosure-only, not ranking.** Google extracts C2PA / IPTC `digitalSourceType` metadata (including `trainedAlgorithmicMedia`) and *may* surface it in "About this image" ([image-license-metadata doc](https://developers.google.com/search/docs/appearance/structured-data/image-license-metadata), updated 2025-12-10; original announcement [2024-09-17](https://blog.google/technology/ai/google-gen-ai-content-transparency-c2pa/)). That page mentions ranking nowhere. Google's SynthID/C2PA detection expanded to Search and Chrome at I/O in May 2026 — still framed as transparency. Mandatory AI-provenance tagging exists **only in Merchant Center** ([ecommerce policy](https://support.google.com/merchants/answer/14743464)), which does not apply to us.

**The spam policies contain no AI-image clause.** [Updated 2026-05-15](https://developers.google.com/search/docs/essentials/spam-policies) — the only AI hook is *scaled content abuse*, which is about volume and value, not medium.

**The one contrary report is weak.** A practitioner ("Zack Notes") posted LinkedIn charts in Jan/Feb 2025 showing image traffic collapse for AI visuals on his site, hypothesising a new Images quality signal ([SERoundtable](https://www.seroundtable.com/google-image-search-down-ranking-ai-images-38892.html)). Barry Schwartz reported not reproducing it. Single source, never replicated, never confirmed. Do not plan around it.

**Bing: nothing at all.** Microsoft's Content Credentials work covers only images *Bing itself generates*. No policy on third-party AI images in Bing Image Search. Their Webmaster Guidelines rewrite (~Feb 2026) actually *softened* the AI stance, and the Bing Webmaster Blog has published no image guidance since 2015. Absence of evidence, but a fairly loud absence.

**The real risk is human, not algorithmic — and it lands squarely on us.** John Mueller, LinkedIn, 2023-12-31, speaking personally: *"If I noticed a recipe site were using AI-generated images, I'd assume all of the content is scraped spam and just go somewhere else."* ([SEJ](https://www.searchenginejournal.com/beyond-seo-john-mueller-on-ai-generated-images-stock-photography/504793/)) He is describing a reader's reaction to a recipe site with AI photos. That is this site. It costs nothing in the index and possibly everything in trust — including with the exact journalists whose links are the site's real upside (A12).

### 6.2 The structural argument, which is the real answer

Split the assets in two, because they are not the same bet.

**The 234 AI-generated food photos: essentially zero ceiling — via deduplication, not punishment.**

The mechanism that actually hurts here is documented, and it is not a penalty. Google shipped an update specifically to collapse duplicate and near-duplicate images (rolled out Nov 2020, [confirmed by SearchLiaison 2021-02-11](https://searchengineland.com/google-image-search-update-reduces-duplicate-image-results-346036)): *"We made an improvement to Image Search to reduce duplicate images, so that we can display others that are relevant yet visually distinct."* Mueller's gloss, on reused imagery: *"you're kind of in the same group with everyone else"* — and `rel=canonical` is not honoured for images, so you cannot choose which copy wins.

A generic AI photograph of black beans in a bowl lands in exactly that group, alongside every stock library, every food blogger's phone camera, and every other generator answering the same prompt. Nothing about *our* black beans is what anyone searching "black beans" wants. And the tiebreak within the group falls back on page strength, which we do not have.

Important caveat in the other direction, because it undercuts the tidy version of this story: **Mueller also said (2021-09-09) that "with images in particular, uniqueness isn't equivalent to higher quality."** There is no *boost* for being original. This is a selection-among-duplicates problem, not a scoring one.

**The 31 original charts: small, but real, and the only part worth effort.**

"Bar chart ranking the top 20 cheapest high-fiber foods by grams of fiber per dollar" is an image nobody else has, answering a query nobody else can answer. Three defensible reasons it is the better asset:

1. It sits **outside every dedup cluster** — there is no group to be lumped into.
2. It answers `X per dollar chart`-shaped queries that no photograph can answer.
3. Data-led formats are historically the most link-attracting content type — Backlinko/BuzzSumo's 912M-post study ([2019-02-19](https://backlinko.com/content-study)) found infographics and "why/what" posts earn *"25.8% more referring domain links"* than how-tos and videos.

**But I have to be straight about the limit of that argument: there is no study, no Google statement and no dataset showing that charts outrank photos in Google Images or image packs.** Ahrefs, Semrush, Sistrix, seoClarity, Advanced Web Ranking and the academic literature all segment image-search performance by everything *except* image type. It is a genuine gap. The three reasons above are sound reasoning; "original charts rank higher than photos in image search" is a sentence nobody can currently support, and I am not going to write it.

*(A note on sourcing: several 2026 SEO aggregator sites circulate figures like "original research earns 6.4× more backlinks" and "interactive data viz: 487 referring domains vs 62." I could not trace any of them to a primary BuzzSumo or Ahrefs publication. Treat them as fabricated. The 2019 Backlinko figure above is the only one that survives checking, and it is seven years old and correlational.)*

**The headwind nobody has priced in yet.** On Google Images' 25th anniversary, [2026-07-14](https://blog.google/products-and-platforms/products/search/google-images-25th-anniversary/), Google began **generating its own images inside AI Overviews** (the Nano Banana model) rather than retrieving publishers'. Generated visuals carry no attribution and no outbound click ([Search Engine Land](https://searchengineland.com/google-ai-overviews-now-lets-you-create-image-482163)). That is two weeks old and its effect is unmeasured, but the direction is unambiguous and it points down. Earlier AI Mode visual results did link out ([Google, 2025-09-30](https://blog.google/products-and-platforms/products/search/search-ai-updates-september-2025/)); the newest surface does not.

The charts' real payoff is second-order anyway, and it survives all of this: a chart is the thing a personal-finance journalist screenshots. Every chart that gets found is a link that might follow.

### 6.3 The number

**First, an honesty warning about the benchmark itself: there isn't one.**

I went looking for "what share of organic traffic does Google Images deliver for a small food site" and the answer is that **no credible published figure exists** — not for small sites, not for food/recipe, not in aggregate. Every large clickstream study bundles Google Images with YouTube and Maps into one "Google properties" bucket. The widely-repeated "~20–25% of searches are image searches" traces to **Jumpshot clickstream data from 2017/2018**, and Jumpshot shut down in January 2020 — nobody has refreshed it in eight years. It also measures query volume, not referrals. Claims like "optimized image libraries see 20–40% of organic traffic via image search" are untraceable and should be treated as fabricated.

The best real anchor is Glenn Gabe's first-party GSC data ([2020-10-14](https://www.gsqi.com/marketing-blog/image-pack-rankings-in-google-web-search/)): image search converts impressions to clicks roughly an order of magnitude worse than web search — one query at ~3,000,000 impressions returned **430 clicks**. seoClarity puts image-search CTR "less than 0.5%". Both are illustrative, not benchmarks.

**My estimate, months 1–12: 20–120 visits/month, and I would bet on the low half.**

That is *below* the traffic sweep's 20–200 for B4, deliberately, for four reasons:

1. Nine (now sixteen — see §7) articles currently ship a broken hero. Fix that before anything else.
2. AI food photos are commodity content and they are ~88% of the library, so most of the library is dedup fodder.
3. The 2026 zero-click environment (~68% per the sweep's B1 sourcing) hits image search at least as hard as web search.
4. AI Overviews began generating their own images two weeks ago (§6.2). Unmeasured, but the direction is down.

Split roughly: **charts 15–90/mo, AI food photos 5–30/mo.** Time-to-first-signal 3–6 months — the images have to be crawled, and until this pass the charts had no discovery route beyond an unannotated `<img>`.

**Say it plainly: this channel will not change the site's trajectory.** 120 visits/month at image-search engagement quality is worth less than 30 visits/month from Bing organic (D1, 50–500/mo). The reason to do this work anyway is that it cost one afternoon, most of it was bug-fixing that had to happen regardless (a broken `<picture>`, sixteen 404 heroes, 49 CLS-inducing charts), and the chart half feeds the link-acquisition play in A12, which is where this site's actual upside lives.

### 6.3b Measuring it — one landmine

When you check this in Search Console, use **clicks only, and only dates after 2026-04-27.**

Google over-reported impressions from **2025-05-13 to 2026-04-27** — a ~50-week logging error affecting impressions, CTR and average position. Clicks were unaffected. **Historical data was never corrected**, only fixed going forward. ([Search Engine Land, 2026-04-03](https://searchengineland.com/google-search-console-bug-inflated-impression-counts-473530); [fix confirmed 2026-05-04](https://searchengineland.com/google-fixes-search-consoles-year-long-data-logging-issue-well-kind-of-476442).) At least one practitioner reported the inflation was most visible in Image Search specifically, though Google never said so — treat that as unverified.

So: Performance → Search type = **Image** → **clicks**, compared against Search type = Web, post-2026-04-27. Anything else will flatter you.

### 6.4 What I would NOT do

- Do not commission more AI food photography for image-search reasons. Zero marginal return, and Mueller's recipe-site remark (§6.1) says the reader-trust cost is real.
- Do not add AVIF. No ranking effect, ~+7 min per deploy.
- Do not tag our images with C2PA `trainedAlgorithmicMedia` for SEO reasons. It is disclosure metadata with no ranking effect, mandatory only in Merchant Center, and it would hand a "this is AI" label to the "About this image" panel for zero search benefit. If we ever do it, do it because it is honest, not because it ranks — it doesn't.
- Do not add `license` / `acquireLicensePage` markup until the CC BY reversal (`207442c`) is understood. Same blocker as Dataset Search.
- Do not rename the 234 heroes (§2.1).
- **Do** make more charts. Every new one is a unique asset outside every dedup cluster, they cost minutes from the existing CSVs, and they are the only image class here with a defensible position.

### 6.5 What could not be verified

Stated so nobody treats reasoning as evidence:

- Any published figure for Google Images' share of clicks in any vertical. **Appears not to exist.**
- Any study comparing charts vs. photographs in image-search performance. **Does not exist.**
- Any measured traffic effect of the 2018 "View image" button removal. No rigorous study was ever published; if anyone cites a number, ask for the source.
- Any Microsoft statement on labelling or demoting third-party AI images in Bing Images.
- Whether AI Mode / AI Overview image results send meaningful clicks. Nobody has published data.
- The 2013 Google Images redesign is the one large measured event (Define Media Group, 87 sites, **−63%** image referral traffic, [2013-04-15](https://searchengineland.com/study-google-image-search-referrer-traffic-drops-63-since-upgrade-155879)) — but **Google publicly disputed it** and it was never independently adjudicated.
